# 平台概述

> **文档编号**: 01
> **抽象层级**: 产品愿景 / 整体蓝图
> **状态**: 初稿

---

## 一、这是做什么的

iGEM Silk Platform 是一个**丝素蛋白融合功能肽设计的可视化平台**。

科学家（实验人员或团队内部研究者）在网页上：
1. 选择功能类型（抗氧化/抗菌/抗糖化等）
2. 配置筛选参数（或使用预设方案）
3. 一键触发完整 Pipeline 运行
4. 实时查看漏斗进度 + 日志
5. 得到最终排名结果，对比不同设计方案，浏览 3D 结构

本质上是将现有的 `stages4` Pipeline（19.9M → 250 constructs，8 轮评分 + 3D 预测）包装成可操作的 Web 应用。

---

## 二、为什么需要这个平台

**现状**：
- Pipeline 通过命令行脚本运行，需要懂代码的人操作
- 结果分散在 `output4/` 目录的多个 CSV/DB 文件里，不直观
- 多方案对比需要手工整理数据

**目标**：
- 实验人员可以自主运行 Pipeline，不需要写代码
- 结果可视化（漏斗图、排名表、结构浏览），可以直接用于汇报
- 配置方案可复用，方便不同实验条件对照

---

## 三、目标用户

| 用户 | 角色 | 主要操作 |
|------|------|----------|
| 实验人员 | A | 上传序列（可选）、选功能类型、触发运行、查看排名 |
| 科学家 | B | 调整参数配置、对比不同方案结果、浏览 PDB 结构 |

两类用户在 Phase 1 都会使用同一套页面，但使用深度不同（A 用层级 A 配置，B 用层级 B/C 配置）。

---

## 四、分阶段交付

### Phase 1 — MVP（最小可用版）

**目标**：用户可以完整跑完一个 Pipeline 并看到结果。

- 用户注册 / 登录
- 在前端选择功能类型 + 配置参数（层级 A/B/C 可选）
- 触发 Pipeline 运行
- 实时看到漏斗进度可视化 + 可展开的日志流
- 运行完成后看到排名结果表格（Linker 类型 / 位置方案 / 功能肽序列 / 各项评分）
- 查看某个 construct 的基本信息（不包含 PDB 浏览）

**不做**：结构浏览、配置保存/复用、结果对比

---

### Phase 2 — 完整功能版

在 Phase 1 基础上增加：

- **配置方案管理**：保存/加载/公开分享配置（私有/公开两 Tab）
- **结果对比**：选中多个 run，横向比较排名、漏斗形状、关键评分
- **结构浏览**：NGL Viewer 展示 PDB，旋转/缩放/选择链/导出
- **潜在扩展**：用户管理（Admin）、分享链接、导出报告 PDF

---

## 五、用户旅程（Phase 1）

```
[注册/登录]
    ↓
[首页] 选择功能类型
    ├─ 层级 A：只要选抗氧化/抗菌 → 直接运行
    ├─ 层级 B：选功能 + Top N + Linker 类型 + 3D 工具
    └─ 层级 C：完整参数调整（权重/阈值/位置方案）
    ↓
[触发运行] → 自动跳转到 /jobs/:id
    ↓
[任务详情页] 实时漏斗进度 + 可展开日志
    ↓ (Pipeline 完成)
[结果表格] 按综合分排名，显示关键列
    ├─ 展开查看各服务详细得分
    └─ 点击查看 construct 详情（Phase 1 不含 PDB）
```

## 六、核心指标（成功标准）

| 指标 | 定义 |
|------|------|
| Pipeline 成功完成率 | 触发运行后完整执行到最终排名的比例 |
| 页面加载时间 | 首页 < 1s，任务状态页 < 2s |
| 进度更新延迟 | WebSocket 推送延迟 < 5s |
| 用户完成任务率 | 注册 → 配置 → 触发 → 查看结果 完整走完的比例 |

## 七、与现有 Pipeline 的关系

```
stages4 (iGEM-silk-main)                    平台新增
────────────────────────                    ──────────
main/stages4/s4_round*.py    ←被调用←     Pipeline Scheduler
output4/pipeline.db         ←只读←       Result API
output4/pdb/                ←只读←       Structure API
main/client.py                ←复用←       ServiceClient
main/config.py               ←复用←        配置
tools/docker-compose.yml     ←复用←        微服务
```

平台**不修改**任何现有 `stages4` 代码，只通过 subprocess 调用 `uv run python -m main.stages4.s4_round*`。

平台**只读** `output4/` 下的数据，不触碰现有的 DuckDB 文件。

---

## 八、关键假设（需要验证）

1. stages4 Pipeline 可以在 FastAPI 所在机器上成功运行（环境一致，`uv` 可用）
2. 单 GPU 机器上，Pipeline Scheduler 能正确管理 GPU 资源的获取和释放
3. PostgreSQL 部署在 FastAPI 同机或局域网内，延迟可接受
4. WebSocket 连接在长时间运行（数小时）下保持稳定
