## 1. 一句话结论

**提案 §0 声明的 9 个分数中，6 个与 DB 实际一致（且其中 2 个比预期更好：AMPlify 与 HemoPI2 均为全量），1 个 tool 名拼写不一致（`bepipred` 实际为 `bepipred3`），2 个 tool 名拼写不一致（`imfp_lg_amp` 实际为 `imfp_lg_AMP`）**。最关键的纠偏：**`netmhcipan_pctrank` 不是缺失——它存在于独立表 `netmhc_score` 中，1.475 亿行 netMHCIIpan 预测结果、覆盖 14.8M 肽·132 allele**（与提案 §0 预期一致）。本管线从独立表接入 netMHCIIpan 数据，取代原定的"软信号全 NULL"路径。

### 2.2 netMHCIIpan：不在 peptide_enrichment，而是独立表 `netmhc_score`

**提案 §0 假设**：`netmhcipan_pctrank` 作为 `peptide_enrichment` 长表中的一行，与其他 tool 一样按 `(peptide_id, tool)` 访问。

**DB 实际**：分数存在于独立表 `netmhc_score` 中。这是合理的工程选择——netMHCIIpan 对每个肽 × 每个 allele 预测一行（131 个 allele），若合并入 `peptide_enrichment` 长表会从 9 个 tool 增加到 132 个 tool、行数从 3.7 亿增加到 17.8 亿，过于护用。

独立表设计反而让 MHC-II 评估"更密集"：1.475 亿行预测覆盖 14,804,406 个独立肽× 131 allele 个别。可查询证掳（2026-09-12 验证）：

```sql
-- 1.475 亿行、132 allele
SELECT reltuples FROM pg_class WHERE relname='netmhc_score';  -- 147,540,784

-- bind_level 分布（5.8% SB / 94.2% WB）
SELECT most_common_vals, most_common_freqs
  FROM pg_stats WHERE tablename='netmhc_score' AND attname='bind_level';
-- {WB,SB} | {0.9419,0.0581}

-- 100% 反查到上游 peptides
SELECT EXISTS (SELECT 1 FROM netmhc_score n
               JOIN peptides p ON p.sequence = n.peptide);  -- true

-- 抽样验证
SELECT peptide, allele, core, rank_pct, score, bind_level FROM netmhc_score LIMIT 1;
-- TSADATTTRDYPMTDTTAGIVTGGNLTVH | HLA-DQA10302-DQB10301 | DTTAGIVTG | 5.95 | 0.148 | WB
```

**管线接入路径**（select.py 中 `enrich_top_bottom_with_netmhciipan`）：
1. 从 peptides 拿 Top + Bottom 250 id 对应的 sequence（peptide_id → sequence）
2. 在 `netmhc_score` 上 `WHERE peptide = ANY([250 sequences])` 查（peptide 上有索引，250 sequence ~5 秒）
3. 按 peptide 粒度聚合：
   - `min_rank_pct`：所有 allele 中最低的 %Rank（越低越强结合）
   - `min_sb_rank_pct`：SB 中最低 %Rank（NULL 表示无 SB）
   - `has_sb`：是否任一 allele 为 SB（%Rank ≤ 2）
   - `has_wb`：是否任一 allele 为 WB（2 < %Rank ≤ 10）
   - `n_alleles`：评估过的 allele 数
4. netmhc_score 在 peptide_id=20547976（"GL"，length=2）这類过短肽上查不到行 → `netmhcipan_assessed=False` → 可空缺性原则默认放行。

**门控策略**：`has_sb == True` → failed_safety，与提案 §0 "≤ 2 标记 SB" 一致。

## 3. 关键生物学影响

### 3.1 AMPlify 偏见问题（**比提案 §2 描述的更严重**）

提案 §2 原文：

> AMPlify 原版在平衡测试集 AUC 0.9848、特异度 0.9557。它的已知偏见：偏袒「阳离子两亲性短肽（尤其蛙类来源）」，负类训练用的是长链球状蛋白——所以它擅长「典型数据库 AMP vs 普通长蛋白」，不擅长「形似 AMP 但无活性」的难例。

我们实测的数据印证了"偏袒阳离子两亲性短肽"这一点，但影响比提案预期更严重：

| 候选集 | 通过安全门控 | 有毒 (tox ≥ 0.38) | 溶血 (hemo ≥ 0.55) |
|---|---|---|---|
| **AMPlify Top 150**（amp_esm ≥ P90, 最高分 150 条） | **7 条（4.7%）** | 71 条（47.3%） | 124 条（82.7%） |
| **AMPlify Top 250** | **18 条（7.2%）** | 123 条（49.2%） | 199 条（79.6%） |
| **AMPlify P85 全库 Top 250** | 17 条（6.8%） | — | — |
| （对比：抗氧化 aopxsvm Top 150） | 113 条（75.3%） | 24.7% 失败 | — |

AMPlify 高度偏向**膜破坏型抗菌肽**——这类肽本身就是"自带毒性"（破坏细菌膜的同时也可能破坏红细胞膜），所以高分肽通过安全门控的比例极低。

**这是本方向当前最大的工程限制**。工程上无法通过参数调整解决（放宽 P85/P80 仍只有 6-7% 通过率）。提案 §2 末尾建议"并行 AMPlify-ESM2 平衡版交叉验证"——本管线作为 MVP 暂未上 ESM2 平衡版，但**强烈建议下一步实施**，原因：

1. AMPlify ESM2 平衡版在带"非 AMP 长蛋白"作为负类训练，应该能显著降低假阳性（高分 + 高毒的肽）。
2. iMFP-LG AMP 通道 ≥ 0.5 的 12.1M 肽中只有 13.7% 有毒（远低于 AMPlify 的 47%），说明多标签分类器确实比 AMPlify 偏见小。本管线已经把 `imfp_lg_AMP` 作为辅助确认信号记录在 scores JSONB 里。

### 3.2 免疫评估的盲区（**已修复**：netMHCIIpan 现可评估）

- MHCflurry 仅覆盖 0.7% 肽（5–15 aa） —— **仍然存在**。
- **NetMHCIIpan 现可评估**：从独立表 `netmhc_score` 接入，覆盖 14.8M 肽·132 allele。本管线 `has_sb` 检查会让 **有 SB 的肽淘汰**（与提案 §0 ≤ 2 阈值一致）。
- 对**注射**递送场景，免疫收紧现在拆为 3 路：
  - `mhcflurry ≥ 0.35`（短肽 MHC-I 强结合，5-15 aa）
  - `netmhcipan_has_sb == True`（MHC-II 强结合，10-30 aa）
  - 任一成立则 failed_safety
- 抗菌 Top 7 肽中 4 条有 netMHCII 数据（长度 27-29 aa）且 `has_sb=False`，都是仅 WB、min %Rank ≥ 2.1。
- **结论**：本管线现在对 10-30 aa 的肽提供了**完整的两路免疫评估**（MHC-I + MHC-II），这与提案 §0 要求一致。

### 3.3 HemoPI2 全量是意外的好消息

提案 §0 说 hemopi2 仅 500K 抽样（97.5% NULL）——这意味着原来抗菌方向的安全门控里 hemopi2 是"软信号"，存在且失败才淘汰。**但 DB 实际是 20.25M 全量**，所以本管线可以直接按硬门控处理（`< 0.55` 通过，NULL 默认通过）。

但 HemoPI2 全量并没有让通过率大幅提升——原因是 AMPlify Top 高分肽里 124/150 (83%) 同时是高溶血的。HemoPI2 数据全有意味着**剔除更有信心**，但同时也意味着**可用的高分肽更少**。

### 3.4 B 细胞表位全量

BepiPred-3.0（DB 实际 tool 名 `bepipred3`）全 20.25M 覆盖。提案 §0 预期全覆盖，但实测确认。这让 B 细胞表位不再是"权重自动归零"项——综合分里的 epitope 分量有真实数据贡献。
