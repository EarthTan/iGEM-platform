## 1. 提案原样照搬的可行性：5 处偏差（v1 含 netMHCIIpan 接入）

| # | 提案假设 | DB 实际 | 工程修正 |
|---|---|---|---|
| 1 | `igem_peptides` 宽表，9 列分数 | `peptide_enrichment` **长表** `(peptide_id, tool, score, ...)` | 提案 §1 SQL 全部要重写 |
| 2 | `amplify` 来自历史 TSV，覆盖待确认 | 实际 `tool='amp-esm'` 全 20.25M 已存在 | 直接全表查询，候选池 SQL 用 `tool='amp-esm'` |
| 3 | `bepipred` 全覆盖 | DB 实际 `tool='bepipred3'`（拼写差异） | 工程上重命名为 bepipred3，scores JSONB key 也用 bepipred3 |
| 4 | `netmhcipan_pctrank` 在 peptide_enrichment 中 | DB 实际是独立表 `netmhc_score`（1.475 亿行·132 allele·14.8M 独立肽） | select.py 加 `enrich_top_bottom_with_netmhciipan`：从 250 个 sequence 在独立表查 + peptide 粒度聚合。门控逻辑在 `apply_safety` 与 `composite` 中接入 |
| 5 | `imfp_lg_amp` 交叉验证 | DB 实际 tool 名 `imfp_lg_AMP`（**大小写敏感**，大小写不是同名） | 工程上重命名为 `imfp_lg_AMP` |

工程上的修正路线：

1. 候选池 SQL 改用长表查询（`tool='amp-esm' AND score >= p90`）
2. 不建宽表，沿用 antioxidant 的"先选 Top250 id，再主键 enrich"的策略
3. 缺失的 tool 列按"可空缺性原则"放行，记前端"未评估"
4. tool 名差异通过工程化重命名解决（bepipred → bepipred3，imfp_lg_amp → imfp_lg_AMP）
5. **netMHCIIpan 从独立表接入**，保留肽粒度聚合而非全表拉取

## 2. 阈值口径最终选择

| 维度 | 提案（管线文档） | README §三 第五项 | 最终选择 | 原因 |
|---|---|---|---|---|
| `toxinpred3` | `< 0.38` 通过 | `< 0.38` 通过 | **0.38**（一致） | 产品对外口径 |
| `hemopi2` | `< 0.50` 通过 | `< 0.55` 通过 | **0.55** | 产品对外口径；0.50 偏松 |
| `mhcflurry` | "≥ 0.87 只标记，WHERE 不淘汰" | `< 0.50` 才通过 | **`< 0.50` 通过 + 注射 `< 0.35`** | 产品口径；99.3% NULL 时硬门控为空集，但 NULL 仍放行 |
| `netmhcipan_has_sb`（独立表聚合） | "≤ 2 标记 SB" | 未明确 | **SB 命中任一 allele → 失败** | 门控与提案 §0 一致 |
| 注射收紧 | "flag_mhci 非零即 failed_safety" | "0.35" | **0.35** | 产品口径 |
| `amp_esm` 主排序 cutoff | `amplify >= 0.5`（隐含 P90+） | 未明确 | **P90 = 0.4906** | AMPlify P50 = 0.04，P90 = 0.49；若固定 0.5 阈值仅得 1.94M 候选，与"接近全库前 10%"一致 |

## 3. 提案 SQL 在长表上的重写

提案 §1 给出的候选池 SQL：

```sql
SELECT id, sequence, length, source, amplify,
       toxinpred3, hemopi2, mhcflurry, netmhcipan_pctrank,
       plm4cpps, algpred2, bepipred, ...
  FROM igem_peptides, p90
 WHERE (toxinpred3 IS NULL OR toxinpred3 < 0.38)
   AND (hemopi2    IS NULL OR hemopi2    < 0.50)
   AND (amplify    IS NULL OR amplify    >= 0.50)
 ORDER BY amplify DESC;
```

不能直接执行，因为：

- 表名 `igem_peptides` 实际是 peptides（只有元数据）；分数在 peptide_enrichment。
- 9 个相关子查询 PG planner 无法去相关 → 实测 30+ 分钟无法收敛。
- DB 里 `amplify` 实际名为 `amp-esm`；`bepipred` 实际名为 `bepipred3`。

**重写后**：

```sql
WITH p90 AS (
    SELECT percentile_disc(0.90) WITHIN GROUP (ORDER BY score)::float8 AS cutoff
      FROM peptide_enrichment
     WHERE tool = 'amp-esm' AND score IS NOT NULL
)
SELECT e.peptide_id, e.score AS amp_esm, e.label AS amp_esm_label
  FROM peptide_enrichment e, p90
 WHERE e.tool = 'amp-esm'
   AND e.score >= p90.cutoff
 ORDER BY e.score DESC
```

**单 SQL 63 秒**出 2,024,889 行（候选池 = 全库前 10%）。

## 4. 关键工程决策：250-id 主键 enrich + netmhc_score 独立查

### 4.1 为什么不能拉全表 enrich

候选池 2.02M 行，对每个 tool 用 `WHERE peptide_id = ANY(%s)` 查询 2M 个 peptide_id：

- 走 `peptide_enrichment_pk` 主键，理论应该快；
- 实测：planner 选 bitmap heap scan，**VACUUM 缺失时单 tool 30+ 分钟**。

### 4.2 解决方案：250-id 主键查询（沿用 antioxidant）

候选池里只需要 Top 150 + Bottom 100 = 250 个肽做最终落库。**对 250 id 查 8 个 tool 列**：

```python
for tool in tools:
    sql = f"SELECT peptide_id, score FROM peptide_enrichment " \
          f"WHERE tool = '{tool}' AND peptide_id = ANY(%s)"
    cur.execute(sql, ([250 ids],))
```

走主键 `(peptide_id, tool)`，单 tool 查询 **0–15s**（其中 `bepipred3` 较慢——14.7s；其他 tool 都在 0.1s 内）。

### 4.3 netMHCIIpan 独立查询（v1 接入）

netMHCIIpan 分数在独立表 `netmhc_score`，肽 × allele 粒度存储（1.475 亿行）。**不能**在 peptide_enrichment 中拉取（该表中不存在）。

接入路径（select.py `enrich_top_bottom_with_netmhciipan`）：

```sql
-- 先从 peptides 拿 sequence（peptide_id → sequence，毫秒）
SELECT id, sequence, length FROM peptides WHERE id = ANY([250 ids])

-- 再从 netmhc_score 按 peptide 粒度聚合（peptide 上有索引，~5 秒）
SELECT peptide,
       MIN(rank_pct)                                  AS min_rank_pct,
       MIN(rank_pct) FILTER (WHERE bind_level='SB') AS min_sb_rank_pct,
       BOOL_OR(bind_level='SB')                      AS has_sb,
       BOOL_OR(bind_level='WB')                      AS has_wb,
       COUNT(*)                                      AS n_alleles
  FROM netmhc_score
 WHERE peptide = ANY([250 sequences])
 GROUP BY peptide
```

实测性能：250 sequence 查 5.2 秒，匹配 134/250（其余 116 个肽长度不在 10-30 aa 范围内，netMHCIIpan 不预测）。

### 4.4 性能对比

| 方案 | 时间 | 备注 |
|---|---|---|
| 提案照搬（9 个相关子查询 20M 行） | 30+ 分钟 / OOM | 失败 |
| 全表 enrich（每个 tool 拉 20M 行） | 30+ 分钟（无 vacuum） / 1.7s（有 vacuum） | 不稳定 |
| **250-id 主键 enrich + netmhc_score 独立查** | **31 秒** | 选中方案 |

## 5. PG 性能的两个关键 SET

```sql
SET enable_seqscan = off
SET enable_bitmapscan = off
```

`peptide_enrichment` 表 97 GB、planner cost 估算常常失误（实测代价被低估 1000×）。强制走 `(tool, score DESC NULLS LAST)` 索引扫，否则会陷入 seq scan 或 bitmap heap scan。

实测对比（v1 跑完后复验，VACUUM 状态已恶化、较v0 慢）：

| 查询 | 默认 plan | 强制 plan |
|---|---|---|
| `WHERE tool='amp-esm' AND score >= p90`（2M 行） | bitmap heap scan，超时 | index scan **8.8s**（VACUUM 后升到顶状态） |
| `WHERE tool='bepipred3' AND peptide_id = ANY(250)` | bitmap heap scan，14.7s | index scan **14.7s**（VACUUM 缺失下仍较慢） |
| 其他 7 个 tool × 250 id | < 0.1s | — |
| `netmhc_score WHERE peptide = ANY(250)` | peptide 索引 | 5.2s |

## 6. AGGRESCAN a3v 一维实现（沿用 antioxidant）

与 antioxidant 方向完全相同：a3v(sequence) = mean(a3v_i)，a3v_i 来自 Conchillo-Solé 2007 论文的氨基酸级别表。

250 条肽 × ~30aa = 7500 次字典查，< 30ms 完成。

## 7. Winsorized std 权重（README §三"权重数据驱动"）

```python
def winsorized_std(s, lo=0.05, hi=0.95):
    return s.clip(s.quantile(lo), s.quantile(hi)).std()
```

实测结果（Top 通道的 7 条通过肽）：

| 分量 | 区分度（Winsorized std） | 归一化权重 |
|---|---|---|
| cpp     | 0.2356 | 0.1783 |
| sens    | 0.2640 | 0.2640 |
| epitope | 0.2669 | 0.2669 |
| agg     | 0.2907 | 0.2907 |
| **Σ** | — | **1.0000** |

**与 antioxidant 方向的关键差异**：本方向 4 个分量都有非零区分度（`bepipred3` 已全量），所以权重不会被任何一项"自动归零"。

注意：本管线的 composite 是在**通过安全门控的 Top 7 条**上算的，区分度数据是 7 条肽的——样本极小，权重可解释性弱。如果未来 Top 通过数增加，权重会自动调整。

## 8. 综合分计算（含递送调权）

```python
DELIVERY = {
    'topical':     {'cpp':1.4, 'sol':1.3, 'thermal':0.7, 'immuno':'normal'},
    'nano':        {'cpp':0.7, 'sol':1.4, 'thermal':1.0, 'immuno':'normal'},
    'microneedle': {'cpp':1.0, 'sol':1.4, 'thermal':1.4, 'immuno':'normal'},
    'injection':   {'cpp':1.0, 'sol':1.0, 'thermal':1.0, 'immuno':'tight'},
}

score = Σ(w_k * comp_k * mult_k) * α      if passed_safety and immuno_passed_injection
score = 0                                    if failed_safety or injection_mhci_fail
```

`immuno='tight'` 在 injection 下落地为 `mhcflurry ≥ 0.35 → 0 分`。

**本管线实际效果**：7 条 Top 肽中 MHCflurry 全部为 NULL（这些肽长度 27-29 aa，不在 5-15 aa 范围），所以注射收紧不生效——所有 7 条肽 4 种递送综合分都正常计算。

## 13. 已知工程遗留

| # | 遗留 | 影响 | 建议 |
|---|---|---|---|
| 1 | AMPlify 偏见严重，Top 通过数仅 7 | 抗菌方向可用候选不足 | 上 AMPlify-ESM2 平衡版 或 用 iMFP-LG AMP 作为主排序 |
| 2 | bepipred3 查询慢（14.7s） | 整体耗时大 | VACUUM peptide_enrichment；加每周 cron |
| 3 | peptide_id=123947 等 length=2 极短肽 | 候选里有 length=2 的肽（"GL"），可能不是真实多肽 | 前端 Library 页面过滤 length < 5 |
| 4 | 占位 backbone + linker | 不影响筛选流程，但 `full_sequence` 不是真实融合序列 | 等构造器服务上线后回填真实序列 |
| 5 | Top 7 条的综合分是基于极小样本（n=7） | 权重可解释性弱 | 通过上 AMPlify-ESM2 平衡版增加通过数 |
| 6 | netMHCIIpan 对长度<10 aa 或 >30 aa 的肽不评估 | 少数候选肽（特别是 length=2 的“GL”）会被评估为“未评估”（可空缺性原则默认放行） | 可接受：净MHCIIpan 官方支持 10-30 aa；其他长度本来就不评估 |

## 14. 可重现性

```bash
# 1. 建表（与 antioxidant 共用）
psql -h 127.0.0.1 -U igem -d igem_peptides \
     -f src/setup/sql/12_create_constructs.sql

# 2. 跑
python3 scripts/pipeline/run_antibacterial.py

# 3. 自检
psql -h 127.0.0.1 -U igem -d igem_peptides \
     -f src/setup/sql/14_antibacterial_self_check.sql

# 4. 导出 Top10 + Bottom10 CSV
python3 scripts/pipeline/export_antibacterial_top10.py
```

幂等：第 2 步重复跑只会更新 scores / delivery_scores / rank，不会改变行数。
