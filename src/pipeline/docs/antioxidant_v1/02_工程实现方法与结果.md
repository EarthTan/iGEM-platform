## 1. 提案原样照搬的可行性：3 处不一致

| # | 提案假设 | DB 实际 | 影响 |
|---|---|---|---|
| 1 | `igem_peptides` 宽表，9 列分数 | `peptide_enrichment` **长表** `(peptide_id, tool, score, ...)` | 提案 §1 SQL 全部要重写 |
| 2 | 提案未提"宽表构建"这一步 | 实际需要从长表拼出 9 列 score | 中间需要 join / union |
| 3 | 提案对所有肽都跑分 | netmhcipan_pctrank / bepipred **完全缺失** | 软信号降级 |

工程上的修正路线：
1. 候选池 SQL 改用长表查询（`tool='aopxsvm' AND score >= p90`）
2. 不建宽表，改为"先选 Top250 id，再主键 enrich"的策略（详见 §4）
3. 缺失的 tool 列按"可空缺性原则"放行，记前端"未评估"

|---|---|---|---|---|

## 3. 提案 SQL 在长表上的重写

提案 §1 给出的候选池 SQL：

```sql
SELECT id, sequence, length, source, aopxsvm, anoxpepred_frs,
       toxinpred3, hemopi2, mhcflurry, netmhcipan_pctrank, plm4cpps,
       algpred2, bepipred, ...
  FROM igem_peptides, p90
 WHERE (toxinpred3 IS NULL OR toxinpred3 < 0.38)
   AND (hemopi2    IS NULL OR hemopi2    < 0.50)
   AND aopxsvm >= p90.cutoff
```

不能直接执行，因为：

- 表名 `igem_peptides` 实际是 peptides（只有元数据）；分数在 peptide_enrichment。
- 9 个相关子查询 PG planner 无法去相关 → 实测 30+ 分钟无法收敛。

**重写后**：

```sql
WITH p90 AS (
    SELECT percentile_disc(0.90) WITHIN GROUP (ORDER BY score)::float8 AS cutoff
      FROM peptide_enrichment
     WHERE tool = 'aopxsvm' AND score IS NOT NULL
)
SELECT e.peptide_id, e.score AS aopxsvm, e.label AS aopxsvm_label
  FROM peptide_enrichment e, p90
 WHERE e.tool = 'aopxsvm'
   AND e.score >= p90.cutoff
 ORDER BY e.score DESC
```

**单 SQL 7 秒**出 2,024,889 行（候选池 = 全库前 10%）。

## 4. 关键工程决策：250-id 主键 enrich

### 4.1 为什么不能拉全表 enrich

候选池 2.02M 行，对每个 tool 用 `WHERE peptide_id = ANY(%s)` 查询 2M 个 peptide_id：

- 走 `peptide_enrichment_pk` 主键，理论应该快；
- 实测：planner 选 bitmap heap scan，**VACUUM 缺失时单 tool 30+ 分钟**。

### 4.2 解决方案：250-id 主键查询

候选池里只需要 Top 150 + Bottom 100 = 250 个肽做最终落库。**对 250 id 查 9 个 tool 列**：

```python
for tool in tools:
    sql = f"SELECT peptide_id, score FROM peptide_enrichment " \
          f"WHERE tool = '{tool}' AND peptide_id = ANY(%s)"
    cur.execute(sql, ([250 ids],))
```

走主键 `(peptide_id, tool)`，单 tool 查询 **0–4 秒**（取决于 tool 索引覆盖），总 ~7 秒。

### 4.3 性能对比

| 方案 | 时间 | 备注 |
|---|---|---|
| 提案照搬（9 个相关子查询 20M 行） | 30+ 分钟 / OOM | 失败 |
| 全表 enrich（每个 tool 拉 20M 行） | 30+ 分钟（无 vacuum） / 1.7s（有 vacuum） | 不稳定 |
| **250-id 主键 enrich** | **7 秒** | 选中方案 |

## 5. PG 性能的两个关键 SET

```sql
SET enable_seqscan = off
SET enable_bitmapscan = off
```

`peptide_enrichment` 表 97 GB、planner cost 估算常常失误（实测代价被低估 1000×）。强制走 `(tool, score DESC NULLS LAST)` 索引扫，否则会陷入 seq scan 或 bitmap heap scan。

测试结果对比：

| 查询 | 默认 plan | 强制 plan |
|---|---|---|
| `WHERE tool='aopxsvm' ORDER BY score DESC LIMIT 250` | bitmap heap scan，超时 | index scan **3.5s** |
| `WHERE tool='anoxpepred-frs' AND score IS NOT NULL` | heap scan，超时 | index scan **1.7s** |

## 6. AGGRESCAN a3v 一维实现

提案 §3 要求"按序列实时算"覆盖 100% 的聚集倾向代理。

**算法**：a3v(sequence) = mean(a3v_i)，a3v_i 来自 Conchillo-Solé 2007 论文的氨基酸级别表：

```python
AGGRESCAN_A3V = {
    'A': -0.448, 'R': 0.836, 'N': 0.776, 'D': 0.866, 'C': -0.359,
    'Q': 0.749, 'E': 0.851, 'G': -0.535, 'H': 0.066, 'I': -1.034,
    ...
}
```

250 条肽 × ~30aa = 7500 次字典查，< 30ms 完成。

**生物学说明**：a3v 越高越促聚集（疏水+带电残基多）；越负越可溶。**这是肽级聚集代理**，不是三维结构评估。三维评估（如 A3D）需要全长融合蛋白结构，不在本管线范围。

## 7. Winsorized std 权重（README §三"权重数据驱动"）

```python
def winsorized_std(s, lo=0.05, hi=0.95):
    return s.clip(s.quantile(lo), s.quantile(hi)).std()
```

实测结果（Top 通道）：

| 分量 | 区分度（Winsorized std） | 归一化权重 |
|---|---|---|
| cpp     | 0.2356 | 0.3124 |
| sens    | 0.2267 | 0.3005 |
| epitope | **0** | **0.0000** ← `bepipred` 全 NULL |
| agg     | 0.2919 | 0.3870 |
| **Σ** | — | **1.0000** |

`bepipred` 因数据缺失而区分度自动归零，权重自然归零——这是 README §三铁律的工程闭环：**唯一人工干预只剩 α**。

## 9. 落库 schema 与 INSERT 设计

### 9.1 三张新表（`src/setup/sql/12_create_constructs.sql`）

- `backbone_proteins(id, name, type, sequence, length, ...)`：骨架库（5 个占位）
- `linkers(id, name, sequence, length, flexible_count, rigid_count, rigidity, ...)`：linker 库（6 个占位，对应 README §三的 32-linker 库子集）
- `constructs(id, direction, scenario, backbone_id, linker_id, peptide_id, full_sequence, channel, status, rank, scores JSONB, delivery_scores JSONB, assessed_hemo, assessed_mhci, assessed_mhcii)`

### 9.2 唯一索引保证幂等

```sql
CREATE UNIQUE INDEX constructs_uniq_combo
    ON constructs (direction, backbone_id, linker_id, peptide_id);
```

`INSERT ... ON CONFLICT (direction, backbone_id, linker_id, peptide_id) DO UPDATE` 让重跑只更新 `scores` / `delivery_scores` / `rank`，不重复插入。

### 9.3 scores JSONB vs 9 列

提案 §5 说"九项基线分"——选 JSONB 而非 9 列，理由：

- JSONB 灵活，未来加列无需 DDL
- 前端 `Construct.scores` 是对象，JSONB 直接对应
- 仅在 constructs 这一张表才需要 9 列共存；其他地方仍是长表
- 唯一约束靠 `(direction, backbone_id, linker_id, peptide_id)` 维持，不靠 9 列

### 9.4 assessed_hemo / assessed_mhci / assessed_mhcii

三个 boolean 字段在 SELECT 时计算：

```python
df['assessed_hemo']  = df['hemopi2'].notna()
df['assessed_mhci']  = df['mhcflurry'].notna()
df['assessed_mhcii'] = df['netmhcipan_pctrank'].notna()
```

目的：前端展示"已评估 / 未评估"标签（README §三"覆盖度标记供人工复核 / 未来补算"）。

## 12. 已知工程遗留

| # | 遗留 | 影响 | 建议 |
|---|---|---|---|
| 1 | vacuum peptide_enrichment | 单 tool 查询从 1.7s 退化到 30+ min | 加每周 cron |
| 2 | `peptide_enrichment` 缺 netmhcipan_pctrank / bepipred | 免疫 / B 细胞表位评估失效 | 尽快补算 |
